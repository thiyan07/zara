## Adopted now (small, dependency-free, within policy)

### 1. ADB observation layer — `device/adb_linux.py` + `tests/test_adb_observe.py`

From NexusAndroid / droidjig / omni-use: their act loop is built on an
observe→decide→act step over ADB. Zara adopts the OBSERVE half only.
Deliberately narrower per Zara's device-security policy
(docs/DEVICE_SECURITY.md, `core/builtin_tools.py` parity table: "adb is
detection only"; the phone stays behind the paired-device protocol):

- `adb_available()` — honest PATH detection (absent → refusal, never a
  fabricated device list).
- `list_devices()` — bounded `adb devices -l` inventory (serial, state,
  model caps; 40-device bound).
- `ui_dump()` — one bounded `exec-out uiautomator dump /dev/tty`
  observation → UI-tree METADATA only (text, content-desc, class,
  clickable, bounds center). Streams through exec-out so the phone keeps
  no `/sdcard` artifact and nothing is pulled.
- NO tap/key/screen surface: input injection stays with the paired
  protocol; if the policy ever changes, the computer-use agents above are
  the reference implementations.

Tests (14): pure parsers, malformed-input hardening, bounded timeouts on
every call, exec-out/no-persistence guarantee, banner stripping, absent
adb honest refusals — all fixture-faked, no device required.

### 2. Round-ledger mission pattern — documented decision

From LongHorizon-Harness: long missions run as a series of bounded
rounds, each ending with verification against the REAL environment and a
checkpoint (progress ledger) that the next round resumes from; failures
are fed into the next round instead of aborting. Zara's
`core/missions.py` + `core/jobs.py` already checkpoint mission state;
the staged screen-cast work (§4h of ACCEPTANCE_REPORT) followed the same
ledger discipline live (attempt N's evidence gates attempt N+1). No code
change needed — recorded here so future mission work repeats it.

## Round 2 (same day): post-act verification gaps — investigated & implemented

After the first round, a gap inspection of the live tree found the
act→verify loop incomplete at TWO boundaries. Research was then scoped
to those gaps only (no re-surveying the assistants already covered).

### Gap A — browser actions had no `verify` step

`browser.click/fill/submit` returned a single url/title snapshot; there
was no way to wait for the observable consequence (navigation, spinner,
confirm text). Evidence:

- **Playwright — web-first assertions** (official best-practice,
  https://playwright.dev/docs/best-practices + /docs/actionability):
  "wait on an observable outcome … auto-waiting" vs single-shot manual
  checks. Directly applicable because Zara already runs a bounded
  Playwright worker (`core/browser_tools.py`).
- Playwright MCP agent loop guidance (observe→act→verify loop; "prefer
  waiting on an observable outcome").
- **browser-use** project: post-action LLM-judge rubrics — rejected for
  Zara: a second agent loop with its own model calls would violate the
  single-operator contract (LLM proposes → Core authorizes → bounded
  executor acts → Zara verifies) and add GPU/network load.

**ADOPTED — `browser.wait`** (core/browser_tools.py):
bounded poll (0.2–30 s, 0.5 s cadence) over AND-combined observable
conditions (url_contains / title_contains / text_present / selector_visible);
transient evaluation errors are recorded per-round and surfaced in the
final report; timeout returns `satisfied:false` with untouched page
snapshot — never fakes success. Safety: read-only while waiting
(visibility checks only, no click/fill asserts); the same 500-char
selector guardrail strings apply; restricted/safe permission, no new
capability, auto-registered through the existing `BROWSER_TOOLS` path.
Alternatives rejected: browser-use framework (independent agent —
policy), raw `page.wait_for_url` (url-only, no text/visibility
conditions, exception-based rather than a truthful per-condition
report).

### Gap B — phone-side: observe existed, verification of act results did not

After the paired-device protocol executes a tap on the phone, nothing
validated the consequence. Evidence:

- **iurysza/android-use** (MIT, https://github.com/iurysza/android-use):
  "Get the UI state as structured data, reason about it, execute the
  next action" — the observe→reason→act validation pattern. compatible
  concept; nothing copied (MIT-licensed but implementation-specific).
- **openatx/android-uiautomator-server**
  (https://github.com/openatx/android-uiautomator-server): device-side
  instrumented stub — REJECTED: last commit Jul 2024 (stale), requires
  installing a test server on the device and a long-lived forward; far
  exceeds the verification-only need. Zara's exec-out uiautomator dump
  transport (Stage 24b) covers the same data with zero device-side
  installs.
- **Appium** (architectural decision to evaluate as adapter only):
  evaluated and REJECTED for this gap — the missing piece was
  verification LOGIC over dumps Zara already produces, not a transport;
  introducing Appium's server/graal stack for a pure function would
  violate "no integration merely because it appears in a repository".

**ADOPTED — `verify_ui` + pure `match_state`** (device/adb_linux.py):
validated AND-combined condition list (text / text_contains / desc /
desc_contains / cls / clickable — unknown keys raise, typos fail loudly),
bounded retry (≤3 dumps, ≤2 s intervals, 8 conditions, string caps),
truthful `per_condition` report naming which key broke the closest
matching node, evidence carrying the matched node's text/desc/cls/bounds/
center. Read-only: a failed verification never triggers an act; input
remains exclusively with the paired-device protocol. Policy preserved.

### Deliberately deferred this round

- **Local OCR / screenshot understanding** (gap: no `tesseract` on this
  host; confirmed absent): needs a system-package decision (apt) — a
  dependency/install requires user approval per house rules. The honest
  refusal tier is already Zara's convention (see DESKTOP_A11Y.md
  screenshot backends). Deferred, not dropped.
- **Mission-checkpoint rework**: `core/missions.py` already carries
  steps, checkpoints, approvals, RETRYING states; `core/jobs.py` +
  `core/execution.py` carry idempotency keys and max_retries. No gap
  found that justifies churn.

### What this proves

- **Desktop read path is fast enough**: a full bounded inspect is
  ~336 ms; the freshness re-check `_resolve_node` pays per action is
  ~44 ms; X11-window/tool calls are ~2-3 ms (Xwayland carries them).
  The dominant cost of a desktop ACTION is therefore ~44 ms of
  freshness verification + the action itself — human-scale already.
- **Spawn overhead is the measurable software cost**: one AT-SPI op ≈
  44 ms mostly from `python3` spawn + bus connect (measurement: the
  same 8 reads are ~351 ms as 8 spawns and ~50 ms as ONE batched
  spawn — **≈7× fewer**; P95 stable). That evidence justified the only
  structural software change this round (below).
- **x11 tools are NOT useless on Wayland**: they reach Xwayland
  windows (real measured ~2 ms) — scope note for handlers that
  assumed "wayland → unsupported".

### Adopted this round

1. **Read-batch op** — `atspi_probe.py: op "multi"` + tools layer
   `_atspi_batch(reqs)` (`device/linux/tools_linux.py`): N read-only
   a11y ops (`node`/`tree`/`get_text`, ≤ 8, deadline-bound,
   per-entry failure containment) execute in ONE helper spawn.
   **Structurally write-free**: state-changing ops
   (`do_action`/`grab_focus`/`set_text`) are refused as batch children
   on BOTH layers, so batching can never reorder a write ahead of a
   failed freshness check. Existing ops and flows are untouched
   (additive). Measured effect shown above.
2. **Benchmark harness** — capability/routing report +
   reproducible probes with medians/p95/failures/timeouts and honest
   hardware/fixture/pending labels (fixture tests cover all harness
   logic; real desktop runs logged above).
3. **Freshness no-reuse proof** — `tests/test_adb_observe.py` added
   `test_verify_ui_never_reuses_stale_dumps`: verify_ui re-dumps per
   attempt and attempt-2 evidence may only come from attempt 2's dump.
   (Android-side assessment unchanged: within a mission the paired
   app's snapshot_id contract validates freshness per action
   (`expected_snapshot_id`, `STALE_SNAPSHOT` refusal codes, fresh id
   returned on stale), so in-mission snapshot reuse is safe BY
   CONSTRUCTION, no trust extended by this work.)

### ydotool necessity verdict (unchanged, now evidence-backed)

Necessary ONLY for Wayland input injection: everything else AT-SPI
cannot do is either an X11-window's job (wmctrl/xdotool measured
working via Xwayland — including under a Wayland session) or an
a11y-action target (AT-SPI, owned). Its enabling set is exactly:
`apt install ydotool` + `/dev/uinput` udev rule (`GROUP=input
MODE=0660` or `uaccess`) + `ydotoold` service + membership in the
`input` group → click/type/scroll anywhere Wayland-native. Without
it, the HONEST behaviors already implemented stay: refuse, never fake.
No privileged change was made this round.

###### Round 6 (same day): plan continuation — the mission-reliability gap

Researched against the standing capability matrix: for a "unified
Android+Linux assistant", the plan runner already combines tools with
typed data-passing (`fetch`), per-step approval, and cancellation — the
investigation evidence was:

- Multi-step plans succeeded EXCEPT that an approval hold inside a
  plan made the remainder **permanently dormant**: step i's record was
  approvable (and would run on approval), but the plan's steps i+1…N
  would only ever run if the user re-issued the whole task. The
  mission stayed `WAITING_FOR_PERMISSION` with no path forward.
- Checkpoint/restore (`MissionEngine.restore`,
  `PersistentMissionEngine`) existed but was used ONLY by transfer
  missions — generic plans could not resume.
- Sources compared (against the round-1 survey table): startplanner's
  LongHorizon-Harness round ledger (already documented as pattern-only),
  charlesfrye/minecraft-agent planning loop (harness not adopted),
  OpenInterpreter's action queue (wrong authority shape: executor-side
  queue, not mission-bound), and Zara's own messaging flow, which
  already binds ONE approval to a whole mission sequence
  (`core/messaging.py`) — the plan runner lacked the same completion
  mechanics. Decision: implement **mission-bound plan continuation**,
  no second agent/queue.

### Implemented (evidence-based, additive, same-authority)

1. **Stored plan envelope** — `Mission.plan` (models) +
   `MissionEngine.set_plan/plan_of` (bounded ≤ 16 KiB, refused on
   terminal missions, never truncated into fake data);
   `PersistentMissionEngine` persists it with an in-place additive
   schema migration (`ALTER TABLE missions ADD COLUMN plan`, verified
   against a legacy-schema database in tests).
2. **Hold binding** — when a plan parks for approval, the parked step
   is bound to its REAL execution record id in the mission plan
   (`held: {step, execution_id, tool}`), so a continuation verifies
   what actually happened instead of re-running the step (a re-run
   could duplicate a side effect).
3. **`resume_plan`** (`core/intent.py`) — continues a
   `WAITING_FOR_PERMISSION` plan: inspects the held record through
   `fabric.engine.get`; on `SUCCEEDED` (verified mission+tool match)
   it adopts the record's result for the held step (never re-executes
   it) and re-enters the SAME single plan driver from the next step;
   on `FAILED/CANCELLED/TIMED_OUT/DENIED` it marks the step failed and
   ends the mission honestly; while still pending it refuses with the
   record state; mismatched binding/pruned record/non-parked state =
   honest refusal. Continuation runs under the plan's recorded `who`.
4. **Single driver** — fresh plans and continuations share ONE
   deterministic loop (`_drive_plan`); `_run_plan` is a validating
   entry. One attempt per step still; a mid-continuation approval
   simply parks the plan again (continuable by the same rules);
   fetch bindings re-feed from STORED step results (mission records),
   never invented.
5. **Continuation control** — `POST /v1/missions/{mid}/continue`
   (auth; audit `api/mission_continue`; unknown mission → 404) and
   exact NL phrases ("continue", "continue the task", …) in
   `handle_utterance` that resume the most recent parked mission —
   continuation control, not a capability; nothing bypasses parsing
   or the per-step pipeline.
6. **Tests** — `tests/test_plan_continuation.py` (16): park→held
   binding, resume-before-approval refusal, resume-after-approval
   completes without a re-run (call counts prove it), failed held
   record → honest FAILED (terminal, re-continue refused), unknown/
   wrong-state refusals, fetch-from-stored-result continuation, mid-
   continuation re-park (second independent CONFIRM tool), ghost
   record + non-resumable envelope refusals, NL phrase drive + miss,
   envelope persistence across restarts, oversized-plan refusal,
   legacy-DB migration, HTTP roundtrip incl. 404 + no-duplication,
   mid-flight mission refusing continuation.

Race-safety note: continuation does NOT auto-fire on approval — it
must observe the held record's terminal outcome first; that keeps
"approve → auto-execute the rest" impossible, and the gate remains
policy + per-step authorization.

###### Round 5 (same day): Wayland-native launch verification

Gap closed this round: `desktop.app.open` verified X11 launches
(new wmctrl window) but on Wayland could only report "requested
(…no window verification on Wayland)" — and `wmctrl -l` measurably
returns NOTHING on this Wayland desktop (0 X-managed windows), so the
X11 evidence path is dead here. Feature (additive):

1. **Fast `apps` read op** — `atspi_probe.py: op_apps`: registry
   children + Name ONLY (same read pattern as `op_tree`, minus the
   walk), filter + cap, per-entry failure containment, honest
   `{apps, registry_apps}` or `error`. Read-only by construction.
   Measured (live, 8 samples): median ≈ 50.7 ms vs the full tree's
   ≈ 336 ms — the launch-verification poll costs ~1/6 of a tree walk.
2. **Registry-based verification** — `desktop_app_open` on Wayland now
   takes an a11y-registry app list BEFORE the launch and requires a
   NEW entry whose name matches the launcher id afterwards (same
   freshness shape as the X11 window-count diff; no change to the
   CONFIRM policy). Bounded: ≤ 3 polls × 0.6 s. Outcomes are honest:
   `verified (new a11y-registry app entry matches the launcher)` /
   `requested (no matching registry entry within bounds)` /
   `requested (a11y verification unavailable…)` — never a fake
   'verified'. `_app_matches_name` is word-bounded/dot-segment-based
   (no free substring: 'thing' cannot match 'Something Else'),
   pure and unit-tested.
3. **Bench probe `atspi_apps`** recorded in `scripts/gui_bench.py`
   (+ `tests/test_gui_bench.py`, + `tests/test_desktop_app_verify.py`:
   20 tests over the matcher, `_atspi_apps`, all launch flows on both
   session types, and `op_apps` containment/caps).

Deferred (not invented): multi-window/single-instance reasoning
(single-instance apps may fail to add a registry entry — the result
says 'requested', and the mission layer may retry-verify with a
desktop a11y tree instead), KDE/Wayland-compositor-specific app-id
sources, and any non-GNOME alternative verification transport.

## Round 7 (same day): continuation audit — concurrency/crash-consistency survey, hardening

Question: does mission-bound plan continuation (Round 6) survive
concurrent duplicate requests, restart windows, and crash
consistency? Compared against standard single-flight/actor semantics
(no external source this round; in-repo analysis of the same repos'
mission engines cited in Round 6).

Findings → all implemented (§4n of ACCEPTANCE_REPORT):
1. Scan-then-act race on concurrent `resume_plan` → per-mission
   single-owner lock, deterministic refusal (no queueing, no second
   engine).
2. Step outcome persisted only at the next transition → per-step
   checkpoint (crash-consistency at step granularity).
3. Approved-step record in-memory, mission store on disk → restart
   would lose record verification and invite a duplicate side effect
   on restatement. Adopted the record into the mission AT success
   time (execution-engine adoption hook, bookkeeping only) with the
   stored step as the honest verification; residual crash window
   represented honestly (caution message, no auto-retry).

Verdict: ACCEPT (feature + hardening). Fixtures only.

Question: can the assistant take NL reminders ("remind me to X at

without a second scheduler, a second mission engine, or a model in
the reminder path?

Approach (evidence-first): reused contracts from S12–S47 (one-shot

reused `NotificationManager`, reused audit. New additive module
`core/reminders.py` (store + deterministic parser + service), a steer
in `IntentTurnService` before the parser, wiring in `build_stack`.

Findings → decisions (§4o):
1. Exactly ONE live scheduler job per reminder; recurring reminders
   re-arm the NEXT occurrence at fire time (no unbounded job
   creation beyond existing scheduler semantics).
2. Timezone: explicit `ZARA_TIMEZONE` or machine-local zone stored
   per reminder (no naive-UTC ambiguity across restarts).
3. Ambiguity policy locked by tests: bare 1–11 clarified, period
   words defined, day-part past clarified, bare past rolling
   documented. No silent reinterpretation and no silent guessing.
4. Recurrence stores an explicit (hour, minute[, weekday]) anchor —
   discovered via the DST tests that a gap-shifted occurrence would
   otherwise drag the schedule +1 h permanently; anchor prevents
   drift. Spring-forward folds forward (zoneinfo), fall-back holds
   wall time (25 h epoch delta).
5. Delivery honesty ledger: (reminder, occurrence) dedup survives
   restarts and retries; bounded 3 attempts; recurring misses deliver
   once (no burst) and re-anchor. Ledger recovery, not hook
   availability, is the correctness rule (scheduler `_recover` fires
   before the service exists in `build_stack` — hook NameError is
   tolerated and the service's own startup reconciliation re-delivers).
6. Zero execution authority: reminder text opaque end-to-end (tested
   with command-shaped text).

Verdict: ACCEPT (39 new fixture tests; full suite 1931/1/0, exit 0).

## Round 10 (same day): natural-language capability integration — route on the existing parser, close the approval-grant leak

Question: how should natural-language requests reach the Stage 25
document/clipboard tools without a second dispatcher, and what does
the full request-to-result path actually do today?

Survey patterns (2017-2026):
1. Deterministic pattern routing (alias tables + structural matchers)
   for unambiguous phrasings, with a hosted/LLM path for the rest —
   the established hybrid in production assistants; brittle
   keyword-only routing is the documented failure mode (false
   positives), mitigated by (a) requiring capabilities to be KNOWN
   from Core truth before matching, (b) negative-case regression
   suites, (c) clarifications instead of guesses for ambiguous
   referents.
2. Structural matchers (shape matching) beat broader aliases for
   quoted-payload phrasings: one regex per shape, same precedent this
   codebase already uses for GUI/messaging (`_mechanical_gui`,
   `_messaging_hit`).
3. Multi-turn pronoun resolution ("copy that summary") implemented
   everywhere from result histories to full state trackers; the safe
   pattern is resolving against VERIFIED results only and parking the
   follow-up action behind its own consent — never carrying forward
   authority from the previous turn.
4. Authorization single-use semantics: an approval token that is never
   consumed BY the dispatch it approved is a live-anywhere hazard;
   scoped/bounded consumption (mission-, session-, or
   use-scoped) is the standard hardening.

Findings here (Round 9 integration):
1. Shared capability ids break resolution: descriptors advertise one
   record per capability id, so tools merged under `filesystem.read`
   (`docs.*`, and pre-existing `filesystem.search/extract`) could
   never be resolved by tool name even when a real agent advertised
   them. Same-name capability per tool is the fix (the parity gate
   covers both sides).
2. Proposal parameters are scalar by contract (`check_params`), so
   result-kind narrowing must ride the utterance for response wording
   (filter + honest remainder count), not leak list-typed parameters.
3. A REAL single-turn approval-grant leak existed engine-wide: minted
   grants outlived the approved dispatch because `rec.auth` bypasses
   `decide()`; the next unrelated request harvested them. Fix (no new
   system): non-mission approval mints are used-at-mint; mission
   approvals mint mission-scoped grants consumed only inside THAT
   mission's continuation — which is precisely the Stage 24g
   park→approve→continue semantics the existing tests lock.
4. Anchor-copy follow-ups ("copy that summary to my clipboard") are
   safe only when the payload is bound to a VERIFIED result (mission
   step results, then a bounded in-memory ring) and the follow-up
   still parks for its own fresh CONFIRM grant.

Verdict: ACCEPT (17 end-to-end fixture tests on the real pipeline;
grant semantics regressions green; full suite 2003/1/0, exit 0). No
second dispatcher, no second policy path; the user's real HOME and
real clipboard were never touched.

## Round 11 (same day): truthful verification + no-replay recovery — declared contracts over claimed success

Question: does the existing task lifecycle actually verify what it
executes, and are uncertain outcomes ever replayed?

Survey patterns (1975-2026, distributed-systems verification
literature to agent frameworks):
1. "Executed" versus "verified" are different facts everywhere formal
   (process-algebra traces, reconciliation systems, transactional
   outboxes); systems that merge them eventually report success for
   unverified side effects. The tested pattern: keep BOTH, declare
   per-operation what counts as evidence (schema contract, read-back,
   state assertion), and surface the distinction at every level that
   reports completion.
2. Exactly-once side effects are NEVER guaranteeable end to end for
   external effects; the honest pattern is idempotent-or-refuse: a
   recorded terminal or unknown outcome may not trigger a replay.
   Workflow engines converge on "adoption of recorded facts +
   continuation that inspects, never repeats" — the Stage 24g/24h
   pattern this codebase already has.
3. Schema-verified outputs beat trust-flag outputs for structural
   tools: a declared contract catches agent regressions and malformed
   results BEFORE they reach downstream steps' fetch bindings.

Findings → fixes (§4r):
1. The five docs tools declared verification="none" (unverify-able
   success) — now output_schema with a shared required-key contract;
   clipboards declared "none" despite self-reporting read-back truth —
   now "explicit" (a failed read-back no longer latches verified=True).
2. Mission step outcomes carried no verification verdict; verdicts are
   now persisted (plan["verdicts"]) and merge into BOTH live and
   rebuilt (post-adoption/restart) outcomes, and the DONE message
   lists "succeeded but NOT independently verified" steps.
3. The mission store persisted full clipboard-read payloads, breaking
   the tool's own "no persistence" contract — storage-boundary
   withholding with an honest bounded note; in-flight use unaffected.
4. Device-side error text was dropped from stored step records; now
   carried (step N: failed: <cause>).

Measured (fixture-level): resolver 0.37/0.44 ms median/p95; exactly
1.0 resolve per mission step; 2-step mission turn 3.2 ms; searchtext
turn 3.2 ms (bounded discovery, no cross-boundary cache).

Verdict: ACCEPT (12 workflow tests + 2 contract tests + 3 perf
regression tests on the real pipeline; full suite 2020/1/0, exit 0).
No new verification framework: the existing registry schema check +
fabric verify_device_result + engine records were connected and made
honest; the user's real HOME and clipboard were never touched.

## Round 20 (2026-10-22) — P3d call: what the live conversation taught

1. **The deterministic multi-turn protocol needed a drain step.** A
   parked exec's COMPLETION is asynchronous (in-app approval lands on
   the device job channel, outside the turn process). The flow
   therefore carries the pending exec id in its ring-of-one state and
   consumes the TERMINAL record at the FIRST turn that follows — and
   then applies the current phrase as a directive for the NEW phase
   (approve + "saved as x" in one breath works; the phrase is never
   double-guessed across phase offers).
2. **An accessibility poll is only as honest as the service being
   bound.** The first live run reported verified:false with verdict
   "absent" — CORRECT data, because `enabled_accessibility_services`
   was empty and `focusedPackageNow()` was rootless-null. The value:
   the flow told the truth about not seeing anything instead of
   shipping a manufactured "placed". The fix was an operator grant,
   not code. Lesson recorded: any future window-baed verification must
   FIRST assert the a11y service is bound (or report unsupported
   honestly).
3. **Dial grammar as defense-in-depth works**: the runner refuses any
   number with characters outside `[+0-9*#,,]` INDEPENDENTLY of Core's
   contact-only contract — a bypassed Core still cannot dial untrusted
   text. Tail-mask-at-the-runner means results and audit streams never
   see the full number; the approval prompt remains the only place
   digits exist.
4. **Alias facts are written at the moment the user's confirmation
   pays off** (the second lookup hits), not when asked and not with
   fuzzy evidence — the memory item carries its own provenance
   (`contact_alias` type + the confirmation context in its text).
5. **The pending-flow ring is ring-of-ONE by design**: a newer call
   invitation replaces the older pending conversation — bounded
   state, no queue that grows unattended, and the replaced flow's
   parked approval card remains resolvable in the app (duplicates die
   by TTL, never orphaned).
6. **Emulator infrastructure quirks to remember**: shell `content
   insert` needs `--bind account_name:n:` (null bind) for accountless
   raw contacts; probe the incall screen in its 2–4.5 s lifetime
   window; `content query --projection` takes a comma list but the
   whole projection must survive adb quoting (materialized rows are
   easier to read without --projection).

## Round 21 (2026-10-22) — P3e SMS: the three lessons of a second pass on the same spine

1. **A subclass over the confirm path is cheap ONLY if the hook cuts
   at the right joint.** The first refactor put the hook at the
   confirm-offer — but the "YES → act" dispatch and the parked-result
   report were still call-specific, so the SMS flow inherited call
   wording at exactly the moments a user says "sent" vs "called". The
   full hook set ended up being THREE joints: the confirm line, the
   act (engine.submit call), and the parked-result verdict chain.
   Rule for this codebase: a flow variant must re-own every
   user-visible string and every verdict mapping, not just the offer.
2. **The drain directive layer must NEVER capture free text onto a
   phase whose offer was created in the same turn.** Live sequence:
   drain + "continue the task" — the directive layer saw the new
   draft_ask phase and captured "continue the task" AS THE DRAFT.
   The fix: drain turns pass `from_drain=True` and free-text
   capture is refused there (bounded keywords only: yes/no/alias);
   the offer always reaches the user first. Generalizes to every
   multi-flow phase machine: a phase born this turn is not yet owned
   by the conversation.
3. **App-side infra traps that burned an hour, recorded for the next
   operator**: (a) `pkill -f` with the pattern text inside the same
   bash -c (heredoc included) kills the launcher — kill and launch
   must be separate commands, or use a script file; (b) the app's
   boot-time network probe can cache "offline" when the screen is
   off, and `_tick` refuses to re-probe while the cached snapshot
   says offline → the loop idles forever until a fresh app start
   with the screen awake. This is a REAL robustness gap (a phone
   could strand offline after a screen-off boot); recorded as
   pending app hardening, not silently fixed in-flow.

## Round 22 (2026-10-22) — P3f OTP: consent is a FLOOR, not a grant level

1. **Per-use consent is best expressed as a policy FLOOR the flow

## Round 31 (2026-10-22) — the parked-approval confirm gap: receipts are not slots

Fixing the timer chat loop surfaced a systemic finding about CONFIRM-class
quick actions and how grounding consumed device-advertised schemas:

1. **A tool-level `confirm` field is a receipt, not a slot.** Direct
   callers set `confirm=true` explicitly; the chat path parks a hold
   without it because the user's approval click IS the confirmation.
   Validation then fails at execution ("missing required field:
   confirm"). The two call shapes need different confirm plumbing:
   satisfaction must move to the LAST responsible moment — the engine's
   grant step, after the drift/revalidate binds parked operation
   identity (the pre-approval fingerprint is never re-seen, so the
   receipt injection cannot drift). Asking the user to utter "confirm"
   as a slot value would double-prompt; a parser injecting it would be
   forged authority.
2. **Device-advertised stubs shadowed Core truth.** `build_context`
   merged device-advertised input_schema with the registry schema by
   `setdefault`; a legacy descriptor without a `properties` map won the
   race and silently disabled grounding's missing-required check —
   approvals could park EMPTY inputs and only fail at execution.
   Grounding's authority layer must be the registry (the engine validates
   against it), and the required-check must not ride on the properties
   guard. General rule: when two schema sources merge, the validation
   authority wins over the advertising layer — never vice versa.
3. **Parser direction-rules can misfire on family names.** The generic
   `.set` rule ("start"→enabled=True) would have injected a bogus
   `enabled` slot for "start a timer…" — unknown-field clarify, wrong
   ask. Capability-family extraction rules need precedence over the
   generic rule with an explicit carve-out, and every new quick action
   needs: alias + param rule + grounding review + chat-path live probe
   (not just a tool-level call), because ONLY the chat path exercises

## Round 35 (2026-10-23) — calendar WRITE live; advertising is not routing; the batch-4 decision

Calendar write lessons (feature shipped, §4am):

1. **Advertising is not routing.** The phone's descriptors advertise
   per-TOOL ids, the laptop's advertise FEATURE-level ids
   (`calendar.write`) — so the chat resolver, which routes by
   TOOL name, silently excluded every laptop tool ("no eligible
   device") while the registry said the tool exists. The fix is a
   translation (tool name → required_capabilities → advertised
   feature id) at the three routing points, pinned by tests that
   exercise BOTH directions. General rule: **a resolved "exists"
   somewhere ≠ reachable from the chat path; the routing shape of
   EACH device family needs one live probe before trusted.**
2. **A registry-only tool can never resolve.** The first design put
   `calendar.event.add` in the core-local BUILTINS with
   `supported_devices=["any"]` — but the resolver picks candidates
   from device-advertised capability records only; no device, no
   execution, and "any" is not a device. Laptop-side implementation
   + the parity contract (core def claims linux ⇔ agent implements)
   is the shape that actually executes.
3. **Proxy waits obey the timing invariant, always.** A 15 s proxy
   wait expired jobs before the agent's 25 s long-poll could claim
   them ("device job expired"); the invariant (≥61 s, healthy
   device ≥2 poll opportunities) exists for exactly this. Defaults
   exist; don't override downward.
4. **Approval-triggered writes keep their approval evidence.** The
   exec record's `error` field retains the never-auto park text even
   after a later approval+succeeded — cosmetic residue (status and
   result are the authority), worth a look someday, never a truth
   source.
5. **Workspace hygiene is a dependency.** An external process wiped
   `/tmp/opencode` mid-batch: the launcher script and the
   key-extraction file vanished and the in-memory core (all held
   exec refs) died for good. Both were rebuildable from documented
   contracts, and the peer-device key (persistent state) survived —
   the design principle: **anything needed to boot must be
   reproducible from the repo/docs, never from toolbox scratch
   files; nothing secret should ever live only in /tmp.**
6. **The carried-over decision (from refactoring the write across
   two rounds): event text in chat must be QUOTED.** Unquoted asks
   clarify with the quote template;quoted text is the one unambiguous
   shape a deterministic local parser can own.

## Round 36 (2026-10-23) — RRULE honesty: expand what you understand, label what you don't

Batch 7 (recurring events on the read side) lessons:

1. **Expand-or-label is the only honest pair.** Silently showing one
   base occurrence of a daily meeting while LOOKING complete is a
   confident wrong answer; the pre-fix note ("I don't expand
   recurrences yet") was honest but blanket. The rule: expand the
   subset you understand (DAILY/WEEKLY+BYDAY/MONTHLY + INTERVAL/
   COUNT/UNTIL) and keep the per-event note ONLY for the rules you
   refuse — never a blanket note when nothing is unexpanded, never
   an invented occurrence.
2. **Enumerate-forward walks burn past windows.** The first draft
   walked candidate-by-candidate from the rule's base; a two-year-
   old daily rule exhausted the 400-step budget BEFORE reaching the
   read window — the honest-degradation fallback would then swallow
   a live, perfectly expandable month. Jump-start fixes it: compute
   the interval bucket containing the window start arithmetically
   (FLOOR there — Ceil skipped the base week whose Friday WAS in
   the window; a per-day window filter handles the tail) and walk
   from there. Budget stays as a pathological-case guard, not the
   primary mechanism.
3. **COUNT anchors at the BASE, not the window.** Jump-starting
   must not turn "3 occurrences from creation" into "3 occurrences
   from today" — count-bounded rules walk from index 0 (inherently
   bounded ≤366 candidates), unbounded rules jump.
4. **A recurrence instance keeps its parent's duration.** Hand-off
   semantics: DTSTART decides WHEN, DTEND decides HOW LONG — capture
   both at parse time, apply the end delta to every generated
   occurrence ("in progress" checks included).
5. **Test fixtures that claim "no clock dependence" must prove it.**
   Two rewritten tests shipped with wrong expected values because
   they hand-derived window math (a 7-day horizon silently excludes
   a 14-day fortnight; the base week's in-window Friday starts the

   is written out in the assertion comments.

## Round 37 (2026-10-23) — deletion honesty: verify with the semantics you selected by

Calendar remove (batch 8) lessons:

1. **Verification must reuse the selection's comparison semantics.**
   The first "gone" check (`uid not in bytes`) false-positived on a
   SUBSTRING UID ("p1@x" lives inside "rp1@x"); the title variant
   failed a pinned removal whenever a same-title sibling survived.
   The fix makes "gone" use the exact selector semantics (exact
   UIDs, summary+pin). General rule: **a post-write check is only
   honest when it answers the same question the selection asked.**
2. **A default text read is a line-ending rewrite in disguise.**
   Both calendar tool reads used `open(path, mode="r")` without
   `newline=""` — Python's universal newlines silently turned every
   `\r\n` into `\n` in memory, so ANY subsequent rewrite would have
   normalized the whole operator file. It never fired on the add
   path only because the add tests used LF fixtures. Byte
   preservation is a property of the READ, not the WRITE.
3. **The destructive-word chat guard needs exactly one lawful
   exception, not a rewrite.** The blanket guard refuses
   delete/remove/wipe/… before matchers ever run; a sanctioned
   deletion capability (per-event approval, never-auto-approve)
   needed precisely ONE shape exemption (quoted title + "my
   calendar"), verified in place — every other destructive wording
   keeps the blanket. Blanket guards don't fear blind exceptions;
   they fear un-anchored ones (the exception must route through the
   SAME approval machinery, never around it).
4. **Selector honesty outranks convenience.** Several same-title
   events with no disambiguator → refuse with candidates; a
   repeating parent → the removal says it took the whole series.
   The cost of asking is one turn; the cost of guessing is data.
5. **A full suite on a non-UTC host is a different test than the
   same suite on UTC.** Two tests held clock semantics that only a
   UTC machine confirms: one stamped local now+2h as Z (3.5h in
   the past on IST, passing on second-boundary luck), one assumed
   midnight-anchored windows. Before trusting "passed locally",
   ask what the fixtures assume about the host clock — esp. for a
   personal agent that runs on the operator's real machine.
6. **Local stamps for local questions.** The title lookup answers
   with the LOCAL instant (zone offset shown), because "when is my
   dentist?" is an operator-local question; the 7-day sweep's
   historical Z-stamps stay for continuity but every NEW answer
   format should default to what the person experiences.
7. **History needs a different inclusion rule, not a negated
   guard.** The past ("was") cannot reuse "now <= dt" inverted:
   inclusion by OVERLAP of [day-start, day-end] with the event's
   [start, end] — an event that ran 23:00→02:00 across midnight
   belongs to BOTH days it touched. And the RRULE jump-start anchor
   must move to the past window or yesterday's occurrences were
   structurally invisible (the walker had only ever been asked to
   walk forward from now).
8. **Default-2h was a silent max(), inflating real ends.** The
   "right now" and free-slot logic took max(DTEND, start+2h) — a
   45-minute meeting blocked 2 hours in every derived answer. A
   default belongs ONLY where the field is missing: DTEND present
   → DTEND wins; DTSTART-only → 2 hours AND SAY SO. Defaults must
   never override the truth they exist to back up.
9. **Every verified execution needs an LLM-free answer path.** A
   full reply composed by a hosted model degrades to "Done: <cap>."
   when the model is down — for a READ tool whose deterministic
   numbers are the entire value, that degradation discards the
   answer. Sensitive capabilities need a deterministic formatter so
   the honest reply survives upstream failure (free calendar flows
   already do this — the pattern must extend to every new read).
10. **Digest grouping is a shape contract, not styling.** The sweep
    answers "what's coming"; the digest answers "what happened /
    what does this week look like" — mixing them (a digest that
    silently becomes a sweep, or vice versa) makes the agent feel
    like it didn't hear. Route by the ask's NOUN (week → digest,
    day → scope, next → sweep) and keep each shape honest in its
    own terms (per-day counts, day focus, remaining window).

## Round 40 (2026-10-23) — writes taught the clock; long polls taught silence

(Batch 16: the calendar MOVE, live.)

1. **A write path that stamps local digits as UTC is the tz lie,
   third catch.** The chat write frame ("2pm") stored
   `140000Z`-style values — the local wall clock wearing a Z — while
   every read path labels true UTC. The seam surfaced the moment a
   moved event's label disagreed with the ask: "3pm in" → "20:30
   out". The write side was wrong, not the read side. Rule: the
   stored value must be the REAL UTC instant of the asked local
   time; `astimezone(timezone.utc)` before the Z. Selector pins,
   full pins, and ends all follow (one `_cal_shape`, one frame).

2. **The dispatcher may not hand work to a connection nobody
   holds.** Long polls made claims not-deliverable: the server
   mutates pending→claimed while the HTTP response is still being
   composed; if the claiming client died mid-park, the response goes
   nowhere and the job expires while a LIVE agent polls on, never
   having seen an offer. Task 8's invariant ("a claim comes from a
   live call that will definitely run the job") was broken by the
   long-poll feature, not by the agent. Repair: the owner's
   immediate state probe is the DELIVERY RECEIPT; an unacked claim
   ages into a bounded re-park (redelivery); the delivery cap then
   terminates expired — terminal, never resurrected.

3. **A parked waiter must wake on a defined bound the const-like
   class attribute must be read through self.** A bare
   `JOB_POLL_SLICE_S` reference made every parked long poll die on
   NameError → HTTP 500 → agent swallows → re-poll at full speed
   (196k rounds/80 s) → 429 storms poisoning unrelated endpoints. Two lessons: define the
   slice; and the agent's own bounded backoff on poll errors is a
   separate (still-open) guarantee — the server fix removed this
   trigger, not the whole class.

4. **Instrument the claim, not the suspicion.** Seven theories
   (scheduler races, dual agents, push relays, engine self-claims)
   died against one audit line: the audit log timestamps
   auth_challenges at 1/sec — the fast-fail loop — and register at
   launch. Forensics on the runtime beat reasoning about it.

5. **An edit's diff review must count the bytes it deletes, not the
   bytes it adds.** The batch's first move-function splice clipped
   the `_CLASS_ACTIONS` table between its insertion bounds; the
   batch battery stayed green and the FULL suite caught it (a
   describe NameError). The table was restored from evidence (the
   pins that still name it), proving the pin network works — but a
   splice bounded by "insert before X" without asserting what it
   removed is a silent deletion machine. (ACCEPTANCE §4aw.)

6. **A usually-skipped guard turns a test vacuous.** The morning
   brief's "tomorrow event" test ran its assertions only inside a
   narrow late-night window and passed vacuously everywhere else —
   so its inverted premise (an 18:30Z-literal fixture that READS as
   today 00:00 on the IST host) survived two batches. The first run
   the guard ever allowed was the first failure. Rule: a
   clock-sensitive assertion must be ANCHORED to the live clock
   (compute the fixture from now), not guarded behind a window that
   usually skips it.

## Round 41 (2026-10-24) — the disk-breakdown batch, and a launcher rebuilt from behavior

(Batch 17: `storage.scan` — "where did my disk go", non-calendar by
user direction.)

1. **Adopted idea (interface only): dust/gdu/dua-cli give the disk
   answer as a SHALLOW ranked overview.** (bootandy/dust,
   dundee/gdu, Byron/dua-cli.) What transfers to a chat surface:
   level-N ranked subtree sizes, symlinks never followed, no
   interactivity, top-N only. What does NOT: their TUIs

   (Zara fixes apparent size and NAMES it), their parallel walks
   (stdlib single-thread; the budget makes it honest instead).

2. **Floors are the honest unit of a BUDGETED walk.** gdu/ncdu
   walk exhaustively; a chat assistant must cap the walk (time +
   entries). The correct honesty is not "approximate" but FLOOR
   semantics: `partial=True` + the reason + "sizes are floors,
   items may be missing" — the same floor-truth the category scan
   already had (Stage 20), now applied to directory aggregates.

3. **Nested rankings need per-ancestor accumulation, not summation
   of the finished table.** The first implementation double-counted
   `total_bytes` by summing ALL buckets (parents already contain

## Round 42 (2026-10-24) — the process snapshot; the invariant catches a batch-17 slip

(Batch 19: `system.top` — "what's slowing my laptop".)

1. **A timing invariant is a def-order loop — later loops reach
   later violations.** test_T0 iterates DEVICE_TOOL_DEFS and fails
   on the FIRST tool with timeout ≤60 s. storage.scan (batch 17)
   shipped with timeout=60.0 — `60 > 60` is False — but batch 19's
   system.top (10.0, earlier in the def list) failed FIRST, and
   fixing it let the invariant immediately catch the older slip.
   Lesson: a loop guard reports one violation per run; run it again
   after EACH fix (or make the assert collect ALL offenders).
   Adopted here: fixed both, and the batch-17 timeout moved into the
   same 90 s band as its siblings.

2. **btop's "cpu lazy" is the honest one-shot CPU metric.** Process
   CPU numbers from /proc stat are LIFETIME averages unless you
   diff two samples. For "what's slowing my laptop RIGHT NOW", a
   short sampling-window delta (0.6 s) matches what top/btop show
   interactively without ever running interactively; the window
   length is disclosed in the answer.

3. **Process names are a secret surface — argv is not metadata.**
   cmdline's second argument can literally be an API key the operator
   pasted on a terminal (`python3 api.py --key …`). The snapshot
   keeps the first argument's BASENAME bounded to 60 chars and says
   "full command lines are not kept — names only" in the answer.
   The security principle applied: collect the minimum needed to
   identify, not everything that happens to be readable.

4. **"cpu lazy" ranking also reframes the semantics line.** Windowed
   percentages of TOTAL system cpu (single-core units) must be
   SAID, otherwise a 1.2 % gnome-shell figure reads like "the
   system is idle" rather than a ranking snapshot; the formatter
   states window and units up front.

5. **getaddrinfo does not honor socket timeouts — bounding must be
   architectural.** The first connectivity probe hung the tool
   >40 s on this lab's environment (alive TCP, dead egress): glibc
   resolution has NO timeout parameter, so every probe layer runs
   in a daemon thread joined on a BUDGET and the join timeout BECOMES
   the honest "unreachable" answer. A bounded tool is not one that
   promises fast endpoints — it is one whose worst case is a stated
   constant (documented: ~30 s worst-case wall, 90 s device waiting
   slot).

6. **One blocked endpoint is not evidence of no internet.** The web
   layer probes two keyless URLs and takes the first 2xx; a single
   "limited" reading would otherwise slander a healthy network.
   Verdicts stay descriptive (full / limited_dns / limited_web /
   offline) because the tool measures diagnostic endpoints, not
   "the internet" — the wording must never claim more authority
   than the probes carry.

7. **Pair-restart lesson hardened: the agent registration does not
   survive a core restart.** Every core restart this session left
   laptop-1 "online" (process alive) yet unregistered in the fresh
   fabric (chat says "no eligible device"). The repair is always:
   relaunch the agent after a core restart — and the launcher pair
   now lives in the repo (scripts/start_core.sh) so the wipe cannot
   orphan the sequence again.

## Round 43 (2026-10-24) — the file lens; a display family bug caught by its own filter

(Batch 21: `storage.find` — "which files are over 1 GB".)

1. **A size filter and its display must share one unit family.**
   The floor parsed "1 gb" as 10**9 (everyday decimal) while the
   formatter divided by 1024 and still labeled "GB" — a 4.2e9-byte
   file displayed as "3.9 GB", which reads as BELOW the very floor
   the user asked to exceed. File sizes are now decimal end to end
   (matches how file managers and the ask itself count GB); the
   disk-scan formatter changed with it for cross-surface
   consistency, and the byte fixtures moved from 1024**n to 10**n so
   a relapse fails the tests. Pick the family at the ASK, not at the
   printer.

2. **A recursive aggregator does not scale by recursion.** The
   folder view (batch 17) recurses per level-1 child; the file view
   needs ONE flat ranked set across a deep tree — implemented as an
   iterative explicit stack (depth cap 24 kept as a pathological
   guard, no longer load-bearing). When a bounded algorithm is asked
   for a different shape, restructure the WALK, not just the
   collector.

3. **Paths are the answer when the ask is about files — the
   privacy rule changes with the question.** The process snapshot
   hides full argv (secrets typed on terminals); the file finder
   MUST show full paths (a file answer without them is useless) and
   compensates differently: top_n bounding, house-scope refusal of
   sensitive subtrees, and no deletion suggestions by name. The
   honesty duty is not "minimize output" but "match the
   consequences of the output to the question asked."

4. **A failed record carries the truth in `error`; the formatter
   was reading `reason` first.** The missing-file checksum probe
   answered "I couldn't do that: failed" while the REAL explanation
   ("cannot read …: [Errno 2] …") sat unrendered in the record.
   Repair: reason → error → stage, dict errors unwrap to their
   message, and a bare "failed" is REPLACED by the actual error
   text. Failure wording is not decoration — it is the difference
   between "the tool is broken" and "the file is not there". The
   live re-probe (missing file through the real device path) now
   prints the machinery-wrapped truth; wording inspection beats
   wording polish when they conflict.

5. **A prefix digest must say it is a prefix — and never overshoot
   the stated boundary.** The cap-stop read is clamped to the cap
   (bytes_hashed == 512 MB exactly, digest == digest-of-prefix), so
   "compare full files with the same cap only" is a testable
   invariant, not a disclaimer. Honesty that cannot be pinned by an
   exact fixture is a hope, not a contract.

## Round 44 (2026-10-24) — the growth lens; unit, cap, and shape

(Batch 23: `storage.growth` — "what grew on my disk".)

1. **The ledger must track a stable unit, not the display's top-N.**
   The first baseline stored the scan's top-N across the nested
   union — deep AVD chains flooded it and `.cache` (5.6 GB) was not
   tracked at all, so a real 3 MB change read "nothing changed".
   The display model (top-N, nested buckets, double-count) and the
   storage model (level-1, complete, non-overlapping) are DIFFERENT
   models; pick the storage model by what must stay comparable
   across TIME, not by what looks good in one answer. R41's nested
   double-count lesson, applied a layer deeper.

2. **Size the cap against a measured walk, and thread time from
   entries.** The growth tool refused twice live: first on a 12 s
   budget (the whole-home walk honestly needs ~13 s for 1,024,296
   entries on this host), then on the 400k entry cap which fires in
   2.8 s — raising a TIME budget can never fix an ENTRY bound. The
   entry cap is now a parameter (2M for growth), and the refusal
   still names the fix when a bound is genuinely hit. Defaults are
   guesses until you measure them against the real tree.

3. **A baseline's unit is part of the data's meaning.** Rows saved
   under an older shape (top-N union) are not "wrong baselines" —
   they are not baselines AT ALL for a level-1 differ. The payload
   now carries a shape marker (`level1-v1`); `latest()` treats
   foreign shapes as absent and the next run re-baselines honestly.
   Never diff two snapshots measured in different units, even if
   their fields line up.

4. **State chain exhaustiveness: every fall-through shows up as a
   wrong label.** `grown/shrunk/new/gone/unchanged` as a chained
   ternary fell through "gone" for equal-byte matches. Exhaustive
   state machines deserve if/elif with an asserted-no-else mindset,
   and the fixtures must cover ALL states, not just the interesting
   ones ("unchanged-bucket skipped" is exactly where the bug hid).

## Round 45 (2026-10-24) — calendar compound asks and the conflict lens

(Batch 24: multi-scope day asks + the schedule-conflict check.)

1. **Anchors must match where the phrase sits.** `wants_turn` used
   `re.match` — every alternative is pinned to position 0, so
   mid-utterance conflict vocabulary ("tell me if I have any
   conflicts tomorrow") was invisible and the ask silently MISSED.
   Fix: the conflict vocabulary gets its own SEARCH anchor, GUARDED
   by an action-verb exclusion (cancel/remove/move/add/open …) so a
   mixed control ask ("cancel the dentist if it conflicts") keeps
   routing to the write flows. Lesson generalizes: read-only
   anchors added to `re.match` heads must say WHERE the phrase may
   sit; a search anchor without an exclusion guard swallows
   control asks it has no business answering.

2. **Where two surfaces share words, the more specific owns the
   turn.** "any conflicts this week" first hit the WEEK DIGEST
   (a per-day listing) — answer order is policy: title lookup →
   free → conflicts → week digest → compound → sweep. A generic
   scope check running before a specific check turns one ask into
   another's answer.

3. **Same day words, different honest scopes.** The single-day
   sweep is FORWARD-only ("today" = from now, with a Right-now
   line); the compound multi-day listing and the week digest are
   WHOLE-local-day digests (they include this morning). Both are
   honest; they are DIFFERENT questions. Document the difference,
   never unify silently.

4. **A parser must never raise on a regex-plausible stamp.**
   `to_utc` matched `T011190`-shaped values and then
   `datetime()` raised ValueError — a calendar file with one bad
   stamp could kill a read turn. Now an out-of-range-but-
   well-formed stamp degrades to "unresolved" like an unresolvable
   TZID: broken inputs are DATA, not exceptions.

5. **Craft-reconstruction drift is a structural hazard.** The
   rebuilt launcher (`scripts/start_core.sh`, R41.4) was missing
   `ZARA_ICS_PATH` — the first post-restart live probe answered
   "No calendar configured" from a healthy core. Observed-behavior
   reconstruction is incomplete until EVERY env the live core
   carried is re-derived from the code's defaults, not from
   memory. The launcher now exports the lab .ics path explicitly.

## Round 46 (2026-10-24) — the brief reads five facts now

(Batch 25: morning-brief upgrade — conflicts + reminders sections.)

1. **A composite must reuse, never re-implement.** The brief's
   conflicts line reads `CalendarFlow.conflicts_on_date` — the
   SAME `_collect_pairs` the chat conflict surface uses,
   extracted from `_answer_conflicts` for exactly this. A second
   overlap implementation would drift from the tested one; two
   honest answers about the same calendar must be the same
   computation, or they are lies in waiting.

2. **Sections stay per-section honest.** An unwired reminder
   store says "store not wired" (never an invented zero — absent
   is not empty); a failed read names the reason (`read failed
   (db locked)`); "none pending today (2 later)" keeps the
   future-visible detail an unstated ask tries to hide.

3. **Time filtering belongs to the reader, not the store.**
   `ReminderService.upcoming()` returns everything scheduled; the
   brief filters by due-epoch against the LOCAL end-of-day — so
   "pending today" is the brief's contract, not the store's, and
   the store's evolution can't silently change the section's
   meaning.

## Round 47 (2026-10-24) — the second party in "two-party consent" is the DEVICE

(Batch 26: the phone-side app-open consent surface — released from
item 4's DESIGN-HELD hold. Planned contract, implemented without a
device: live validation deferred until the emulator returns.)

1. **Byte-equal refusal is a device-side property; the expansion adds
   a party, not an exception.** The Phase-1 mirror refused
   out-of-allowlist packages unconditionally — a phone-local guard
   that must NEVER become Core-checkable. The honest expansion keeps
   that refusal as the floor and adds a DEVICE-owned consent on top:
   a real dialog tap on the phone persists a per-package grant in
   SecureStore (Keystore-backed). Core cannot add, revoke, or even
   enumerate grants over the job channel — the store's only consumer
   is the runner, and the revoke lives in the device's own Settings
   card. Core's CONFIRM gate still applies per run; the device
   consent is the SECOND human decision, not a substitute.

2. **Refusal ladders must distinguish their reasons.** Deny
   ("phone consent declined for <pkg>"), dismissal, no-UI-context
   (dialog unshowable), and no-store are four different truths; one
   generic "refused" wording would hide which link broke. All four
   refuse, none invents — and a grant that fails to persist refuses
   the open too: "Allow must never open anything that cannot be
   remembered."

3. **Placement is a UX contract, too.** The device-panel slot in the
   Chat-home list consumed home real estate that the navigation tests
   treat as a budget ("Chat is home" asserts the pairing/talk content
   is in the built viewport — adding a widget below pushed the talk
   panel outside a test's lazy-viewport and broke the expectation,
   which is CORRECT: the home must answer pairing+status first). The
   phone-local policy state belongs on the device's "This device"
   (Settings) card — device-owned surface for device-owned state.

4. **Widget-test substitution needs a call-through double.** A test
   helper that hard-codes the gateway's return shape instead of
   invoking the caller's lambda silently breaks every
   "gateway-touched" assertion (the failure reads as the gateway
   never running). Doubles should schedule the CALL, not just its
   result shape.

Interface hunts: hermes-expense-ledger (SQLite diary + confirm), 
KitchenOwl (grocery lists).

1. **The MarimerLLC shape fits a local-calendar assistant**: the

## Round 53 (2026-10-25) — the emulator LIVE round surfaces five
real defects; each fix is a lesson about state or text that outlives
its writer

The batch-31 live round (detailed in ACCEPTANCE §4bl) turned up:

1. **A dateline bug with the cleanest possible shape**: `free_windows
   ()` built slot datetimes with `now.replace(hour=0,…)` — "now"
   instead of the asked day. The slot LIST looked right (it prints
   times, not dates) and only the PICK re-check carried the dates, so
   the bug surfaced as "your own proposal reads as stale" — the worst
   failure mode for a propose→pick loop (the user did everything
   right). Lesson: a slot must be (date, time) end-to-end; printing a
   time without its date hid the defect from the surface where it
   was born.
2. **A clamp that only exists at one side of the wire**: the sender
   chunks at ≤64 KiB and the receiver that never sent anything under
   64 KiB in tests; Core's `read()` refuses overruns by policy. The
   receiver assumed its own open-ended first read (len 65536) would
   be clamped — policy refused instead. Every size contract needs
   both endpoints tested, including "the smallest possible".
3. **Presence has two sources of truth and one of them never
   heals**: `online` (heartbeat flag) vs `status` (state-machine
   field set only by register/disconnect/gates). A dying agent's
   disconnect can land after its successor's register, and no
   heartbeat ever reset `status` — approvals failed closed forever
   while the device list showed "online". Lesson: derive presence
   from the field that is continuously refreshed, or make the
   refresher repair the stale one. The fix makes heartbeat restore
   `status="online"` precisely when it has proof of life.
4. **Never teach a dead command**: the parked-approval reply sent
   users to "Say 'approve' in the approvals flow" — a route that
   does not exist in the chat parser (and whose keywords are even
   inside the anti-injection guard). Message-string bugs cannot be
   caught by unit tests asserting the string; only running the
   taught phrase live catches it. The message now names the real
   decision surface (the device's approval card), which the round
   also proved live.
5. **A refusal must not consume its own proposal**: schedule-flow's
   `_book` cleared the pending propose before checking the pick, so
   the border-time refusal deleted the list it was about to point
   the user back at; its follow-up advice then landed in the generic
   parser. A conversation state machine's cleanup must happen at
   the point of success, not at the point of attempt — retries
   against the same list are the normal case, not the exception.

Also recorded: the phone-local consent dialog for out-of-allowlist
app-opens is unreachable in the current builds because the Core
enum and the runner mirror are byte-equal — the two-party design
degrades to one check at Core failure time. Reaching the dialog
requires actually diverging the enum, which is a design decision,
not a test artifact. And: the operator token and the device
credential are intentionally separate — the phone's talk surface
auths with the operator token (Keystore-persisted once), device
creds never widen into /v1/talk.
